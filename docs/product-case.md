# Kiwi Trader：让模拟交易研究更容易理解

[体验交互原型](https://dongshuangcheng.github.io/kiwi-trader-showcase/) · [返回项目首页](../README.md)

## 一句话定位

面向个人研究场景，把建议、检查、操作与结果串成可追溯的流程，减少“当前发生了什么、我该做什么”的困惑。

本案例记录本人实际使用与项目问题处理中遇到的场景，再提出面向其他使用者的验证问题。当前没有外部用户访谈或规模化使用数据；不会把个人经历包装成用户调研结论。

## 我在项目中的角色

我的产品侧参与包括提出需求、反馈使用体验、复现问题，以及参与测试与迭代。Kiwi Trader 的原型与大部分工程实现由 Codex 协助完成；本案例重点呈现我如何理解使用问题、权衡产品方案，并设计验证方式。

## 1. 从真实使用时刻出发

以下场景来自我对 Kiwi Trader 的实际使用、问题复现与项目运行记录，不是外部用户访谈结论。公开页面聚焦任务与状态变化；具体标的、账户、持仓、金额、价格和策略参数均留在本地，以合成内容呈现演示。

目标方向仍是需要持续研究、跟踪与复盘模拟交易的个人研究者；这一人群的普遍需求仍需后续测试验证。

| 实际时刻 | 我当时要确认什么 | 产品判断 |
| --- | --- | --- |
| 复盘一条研究建议 | 依据是什么、当时的信息处于哪个时点、流程走到哪一步？ | 将依据、阶段、操作与结果连起来，方便回看当时的判断 |
| 操作请求超时，没有收到回执 | 请求是否到达后台？当前是失败、处理中，还是结果待核对？ | 保留操作上下文，把“未知”与“失败”分开；先核对，再决定后续动作 |
| 电脑休眠或移动断网后恢复 | 哪些盘中时段留下缺口？恢复进度如何？补齐内容属于哪个时点？ | 显示缺采与恢复状态；追补数据保留真实时间，不伪装成实时行情 |

这些经历解释了问题如何进入产品设计，不代表其他用户已经遇到同样困难，也不构成效果提升结论。

## 2. 核心产品目标

优先让使用者回答三个问题：

1. **这条建议基于什么？** 信息和判断有上下文。
2. **现在走到哪一步？** 建议、检查、操作和结果分开表达。
3. **接下来可以做什么？** 异常和限制有清楚的原因及处理路径。

不以增加功能数量、自动化程度或展示收益数字作为这个案例的首要目标。

## 3. 范围与取舍

### 优先支持

- 建议与依据的关联，以及当前阶段的表达。
- 正常、超时、信息过期等关键分支。
- 结果待核对时保留上下文，避免把重复操作当默认路径。
- 可回看的过程记录，以及默认隔离的私人数据。

### 暂不作为公开展示目标

- 投资建议、真实收益、策略有效性承诺。
- 面向真实账户的操作或数据同步。
- 把全部内部参数、技术状态和日志一次性展示给使用者。
- 用“AI 自动完成一切”的说法掩盖规则、限制与人的判断。

### 为什么选择这些重点

最先解决的是理解与控制感，而不是增加自动执行能力。对涉及不确定结果的流程，状态说错可能比信息少一些更有害，因此清楚的反馈与行为边界先于功能扩张。

## 4. 关键产品决策

| 决策 | 为什么这样选 | 放弃或承担什么 |
| --- | --- | --- |
| 依据、阶段与下一步共同呈现 | 减少使用者在不同信息间拼接上下文的负担 | 不把首屏全部留给一个醒目的结论 |
| 明确区分建议与行动 | 避免模型输出被误读为已经执行 | 流程多一个解释层，而不是“一键全自动”叙事 |
| 把“结果待核对”与失败分开 | 没收到回音不意味着操作未发生 | 接受短暂等待，不用错误的确定性换取即时反馈 |
| 保留旧信息，同时标明限制 | 旧信息有复盘价值，但未必适合下一步 | 展示状态和操作资格需要分别说明 |
| 首屏讲任务，细节逐层展开 | 首次访问不必理解全部内部实现 | 进阶内容需要额外一次展开或跳转 |
| 展示原型与真实环境分离 | 展示产品体验不应扩大私人数据暴露面 | 原型不代表真实账户接入或完整生产能力 |

## 5. 原型如何体现这些决策

- **决策回放：** 把一条建议从依据到结果串起来；观察每一步的说明与下一步。
- **异常对账：** 重复请求保持一次模拟提交，补充核对依据后状态收敛。
- **信息时效演示：** 用合成时间值演示保留旧信息、暂停后续动作；静态界面将这种体验放进真实休眠/断网恢复场景，呈现缺采与追补该如何表达。
- **分层阅读：** 产品场景 → 可操作体验 → 设计取舍 → 验证证据；技术边界作为次级材料。

交互输入与数值均为合成内容，流程与问题取舍来自项目的实际使用和问题处理；原型与大部分工程实现由 Codex 协助完成。新鲜度阈值是演示值，不是实际产品参数。

## 6. 已有证据与它的边界

| 已完成 | 能说明什么 | 仍需验证什么 |
| --- | --- | --- |
| 桌面与手机原型走查 | 关键交互可以执行，窄屏布局保持可用 | 真实使用者是否理解、是否满意 |
| 11 项演示逻辑检查 | 典型分支按预期变化，重复请求与核对边界一致 | 生产可靠性、策略效果或业务价值 |
| 公开文件与页面连接检查 | 本次发布仅包含独立展示内容，无真实账户连接 | 任意未来变更都自动满足同样边界 |

当前材料未纳入正式用户访谈、A/B 实验、用户规模、留存或效率提升数字。当前阶段更准确的定位是：**带有清晰验证计划的可交互产品案例**。

## 7. 下一步怎么验证效果

以下为计划，尚未实施。

| 任务 | 观察点 | 可能触发的调整 |
| --- | --- | --- |
| 在不提示的情况下解释一条建议 | 是否能找到依据、分清当前阶段；在哪一步求助 | 调整信息顺序，减少术语，补充状态说明 |
| 处理“结果待核对” | 是否误认为失败；是否反复提交；能否说出下一步 | 修改反馈文案，把核对路径放到更显眼的位置 |
| 判断过期信息是否适合继续操作 | 是否区分可查看与可执行；是否忽略原因 | 加强时效提示与操作状态之间的关联 |
| 回看一条已结束流程 | 能否复述当时条件与结果；查找路径是否曲折 | 精简过程记录，突出依据与状态变化 |

记录任务完成情况、状态理解、重复操作、求助与口头解释。时间仅作辅助观察，避免把“更快完成”误判为“理解更充分”。真实反馈到来后，再决定修改点与复测标准，不预先编造改善幅度。

## 8. 当前反思

- 最初展示偏重实现能力，容易让读者知道“用了什么”，却忽略“为什么需要它”。本轮将产品问题与决策移到主叙事。
- 原型检查可以验证流程与反馈的一致性，但它不是用户验证；两类证据需要始终分开。
- 接下来的优先级应是验证问题假设与信息理解，而不是继续叠加功能和动效。
