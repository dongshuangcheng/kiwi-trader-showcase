从使用场景出发

用户真正需要的，
不只是一个“建议”。

如果研究过程散落在行情、分析和记录之间，使用者就得自己拼出全貌。
这个项目尝试把问题换一种问法：怎样让人理解当前状态，并知道下一步？

设计起点：个人研究场景中的问题假设。当前材料未包含用户访谈或规模化使用数据。

01 / 降低理解成本

先看清理由，
再判断建议。

只看到一个结论，很难判断该不该信。
所以，把建议的依据、当前阶段和后续动作放在一起，而不是让使用者来回找。

走一遍决策过程 →验证关注：能否说清建议从何而来、现在走到哪一步。

      DECISION 01

      先讲清依据

      先解决“为什么”，再展示“是什么”。

      为什么这样选

      单独给出结论会增加判断负担。把依据、阶段和下一步放在一起，比增加更多指标更有助于形成理解。

      怎么验证效果

      计划让试用者解释一条建议的依据与当前阶段，记录是否需要额外提示、在哪些信息间反复查找。

      问题假设信息组织待用户验证
      查看支撑这些决策的系统边界 ↗

      验证思路 / LEARNING PLAN

      先验证走得通，
      再验证是否真的好用。

      原型能运行，不等于用户问题已经被解决。
      已有证据与下一步验证，分开记录。

      已完成 / 原型走查

      关键任务，
      有没有清楚的下一步？

      已走查决策回放、异常核对和信息过期三类场景，并检查桌面与手机操作。验证的是流程可用，不是用户满意度。

      查看验证与局限 +

      已检查

      场景切换、下一步、重置、重复请求与补充证据等交互可操作；手机窄屏没有横向溢出。

      证据的局限

      走查由制作过程完成，尚未替代真实使用者的理解与任务测试。

      已完成 / 场景一致性

      遇到异常，
      反馈是否仍然可信？

      演示逻辑已通过 11 项自动检查，覆盖重复请求、过期拦截与核对后的状态。检查用于保证反馈与操作结果一致。

      查看验证与局限 +

      观察到什么

      重复请求保持一次模拟提交；过期场景在提交前停止；补充证据后不额外提交。

      证据的局限

      只说明合成原型遵守预期规则，不代表真实交易效果、产品留存或商业价值。

      待进行 / 用户任务测试

      使用者真的理解，
      还是只是点到了终点？

      下一步应邀请符合个人研究场景的试用者，在不提示的情况下完成任务；记录误解、犹豫与求助，而不是先追求好评。

      查看计划与判断依据 +

      计划任务

      解释建议依据；处理待核对状态；判断旧信息是否适合继续操作。

      计划记录

      任务完成情况、状态理解是否正确、重复操作、求助次数，以及对“下一步”的口头解释。

      如何据此调整

      若“待核对”仍被当作失败，先修正文案和下一步提示；若信息来回查找过多，再调整层级。尚无真实用户数据或改进幅度结论。

      本案例尚无可展示的正式访谈或对照实验证据，不使用未经验证的提升百分比。

      产品边界 / SCOPE

      让产品被看见，
      让隐私留在边界内。

      展示的是问题思考、产品取舍和可操作的原型。
      真实账户、交易数据与核心业务实现仍保持私有。

      浏览 GitHub 项目 ↗
      公开了什么？

      用户场景假设、设计取舍、验证计划，以及独立编写的前端合成演示。

      哪些内容保持私有？

      核心业务源码、账户、持仓、订单、资金、策略参数、提示词、密钥、运行日志与原仓库历史。

      演示能证明什么？

      它帮助理解设计与流程，不等于用户价值已被验证。当前证据是原型走查和演示逻辑检查；真实使用者的理解、信任与使用效果仍待验证。

      这页会读取或上传我的信息吗？

      演示逻辑不读取文件、不请求业务接口、不使用统计脚本或浏览器存储。页面加载仍由 GitHub Pages 提供，遵循平台自身的隐私政策。
